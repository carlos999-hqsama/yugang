# 插件视觉规范：沿用本 App 的黑白界面

开发前读取本规范；交付前按最后一节逐项检查。它约束新插件，修复已有插件时保留已有区域、尺寸与交互，不借统一主题重排页面。

## 共同外观

左侧菜单名称最多 4 个字（包括汉字、英文字母、数字和符号）。插件制作时使用简短名称；宿主对超过 4 个字的名称统一显示“前 3 个字＋…”（单个省略号，总共最多 4 个字），不换成两行。完整插件名称仍保留在插件管理和无障碍朗读中，不截断保存的 manifest.title。

直接使用 `/framework/v1/base.css` 提供的主题与公共组件，不复制一套 CSS，也不引入外部字体、主题库、渐变背景或装饰性配色。页面只负责业务内容；最左菜单属于宿主，Bot 列表只属于对话页。

| 项目 | 已有框架标准 |
| --- | --- |
| 主背景 / 内容面 | `--ui-bg` / `--ui-surface`，浅灰 / 白 |
| 主文 / 次文 / 弱文 | `--ui-text` / `--ui-text-soft` / `--ui-muted` |
| 主操作 | 黑底白字；其余白底细灰边；一个区域只突出一个主操作 |
| 分隔 | `--ui-line`，不靠厚重阴影区分所有区域 |
| 卡片 / 控件圆角 | `--ui-radius` 14px / `--ui-control-radius` 10px |
| 正文 | 沿用系统字体，13.5px，行高 1.5 |
| 紧凑页头 / 卡片标题 | 公共 `.pg > .ph h1` 最终样式 16px / 卡片 15px，600 左右字重 |
| 整页首页主标题 | `models-header` 风格为宽屏 23px、窄屏 20px；只在独立首页使用一处，不与紧凑页头叠加 |
| 辅助信息 | 12px；版本号放标题旁，基线对齐，不挤在删除按钮旁 |
| 页面留白 / 区域间隔 | 16px / 12–16px；同组控件间隔 8px |
| 输入 / 按钮 | 使用 Input / Button 的默认高度与内边距；图标需有足够触控区域 |

错误、成功、账号在线状态和数据图表可以使用已有语义色。不要将绿色、蓝色或红色用作插件默认主题。不要靠彩色背景、Emoji 堆积和超大标题制造层级。

## 页头类型与尺寸单位

上表全部是 **CSS px**，不是手机截图的物理像素。不要从截图量到 34px 后把 CSS 也设成 34px。公共设置页宽屏主标题为 23px、低于 600px 为 20px。17px 是旧文档未与公共壳最终覆盖对齐的数值，当前紧凑页头最终为 16px。页面内容不能因文档修订而擅自重排。

- 工具、设置、列表详情页：紧凑页头，标题与操作同一行。
- 独立内容首页、概览页：可以使用整页首页主标题，一处大标题＋灰色副标题＋右侧操作。不得另叠一层同名页头。
- 参考某个具体插件布局时，只参考该类信息密度，不自行放大所有标题、卡片或间距。

## 响应式边界

按**插件自己的可用视口宽度**判断，不按整块手机屏幕、物理分辨率或宿主菜单宽度猜测。

| 插件视口 | 约束 |
| --- | --- |
| 小于 600 CSS px | 窄屏；主从页面按导航状态切换为单面板，卡片可单列；按钮不溢出 |
| 600 CSS px 及以上 | 宽屏；既有列表／详情保持左右并排；双列卡片只要实际最小宽度容得下就保留双列 |
| 640、820 CSS px | 不是宿主断点；不得直接用 820 将 796 宽页面切成单列。插件若有真实内容约束，需说明并在断点两侧截图验收 |

若某个插件自己的布局有额外断点，应在该插件内说明；它不是公共框架断点。验收至少覆盖 400、599、600、640、796、820 宽度及所选局部断点两侧。布局应根据实际内容最小宽度决定，不为凑断点制造大片空白。

## 区域与空间

先确定页面属于阅读列表、表单、操作面板或列表加详情，再画出区域。不要把所有软件统一生成为一列横贯全屏的按钮。

- 阅读列表：标题和筛选固定，内容区滚动；每行对齐封面、标题、元信息，长标题可换行，摘要有合理上限。
- 表单：标签清楚，设置分组，用合理最大宽度承载长屏；保存位置稳定，解释就近显示。
- 操作面板：按操作关系选择网格列数，同类按键等宽；结果区与操作区有明确层级。不能把网格应用拆成一个按钮一行的长列表。
- 列表加详情：插件自身可用宽度达到 600 CSS px 时保持左右并排；窄于 600 时按已有返回交互切换列表/详情。判断插件容器宽度，不使用手机物理分辨率，也不再计算宿主菜单宽度。
- 宽屏仍需利用空间：主要内容区伸展，文字阅读区可限制行宽；不能把整个页面限制成一个窄条，让右侧大片空白。
- 高度用容器分配，链路上的 flex/grid 子项设 `min-height:0; min-width:0`。只让指定内容区滚动，不叠加多个无意义的滚动容器。

以下是业务 CSS 的布局写法示例，根类必须换成插件自己的类。它不是新增公共 API，也不要求改造已有页面：

```css
.my-plugin {height:100%;min-height:0;display:flex;flex-direction:column}
.my-plugin__body {flex:1;min-height:0;display:grid;grid-template-columns:minmax(220px, 2fr) minmax(0, 3fr)}
.my-plugin__list,.my-plugin__detail {min-width:0;min-height:0;overflow:auto;padding:16px}
.my-plugin__detail {border-left:1px solid var(--ui-line)}
.my-plugin__actions {display:flex;flex-wrap:wrap;gap:8px;align-items:center}
@media(max-width:599px){
  .my-plugin__body {grid-template-columns:minmax(0,1fr)}
  .my-plugin__detail {border-left:0}
  /* 列表/详情显示状态由页面实际导航状态控制，不同时堆在一页。 */
}
```

## 组件使用

从 `/framework/v1/js/components.js` 导入实际存在的 `Text`、`Button`、`Card`、`List`、`Input`。先看页面接口文档的参数，不猜组件。`Card` 的 children 默认纵向排列；网格或工具面板要传入自己建立的 grid 容器，不能依赖 Card 自动推测布局。需要独有业务控件可写原生 DOM 和局部 CSS，颜色、字体、圆角仍继承主题。

页面 CSS 必须写入 `resources` 且列入 `view.styles`。优先验证样式加载、计算后的布局，再修视觉问题；不能只凭源码“看起来有 CSS”认定成功。

## 必须完整的状态

初次加载、空内容、失败、可重试、正常结果、连续操作后的结果都要可读。等待显示真实进度或小型加载指示，不能伪造百分比。后台刷新保留已读内容，不闪白、不反复刷新整个页面，不突然顶回顶部。错误放在相关内容附近，禁止把原始异常、堆栈或实现说明塞满用户页面。

输入焦点沿用控件圆角边框，不给整段对话套黑色矩形。不要删除按钮键盘焦点；文字和细灰边在浅底上仍要可辨认。按钮禁用、选中与加载状态应有区别。

## 视觉验收：检查实际页面，不检查想象

在专用预览通道完成交互和截图，不切换用户当前页面。预览尚不可用或返回失败时，明确未验，不用生成的设计图代替真实截图。

1. 至少检查 400×720、796×537 两种插件视口，再检查内容较长和输入后状态。尺寸均为 CSS px，记录截图真实尺寸。
2. 检查完整首屏及滚动后的核心区域：无横向溢出、文字截断、控件重叠、大片无用途空白；宽屏应该并排的区域确实并排。
3. 实际点击、输入、滚动，确认焦点不抢走、状态正确、按钮不是空壳；截图中的内容与所测数据一致。
4. 与框架组件和既有页面对照字体、留白、圆角、边框、对齐。不能只通过 DOM 测量就声称“视觉好看”。必须读取返回的截图；模型没有图片读取能力则注明视觉待验。
5. 交付只列真实通过的检查、可打开的截图/报告和剩余限制。出现视觉问题先修当前插件，再复测；不能靠向用户解释“框架如此”交付明显错误的排版。
