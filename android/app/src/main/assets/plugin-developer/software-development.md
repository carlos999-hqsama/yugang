# 在本 App 内开发软件

这是通用开发流程，适用于用户提出的任何插件需求。不要把一个具体工具的实现当成开发能力，也不要要求用户为每种软件重新教你界面和工程规范。

## 先理解交付物

先用一段简短说明明确：用户要完成的操作、输入与输出、需要保存的数据、页面主要区域、成功标准。沿用用户已有布局；只有关键缺失信息会改变需求时才提问。普通的软件常识自行落实，不用连续提问代替实现。不要扩充用户没有要求的功能。

查看实际安装包、宿主契约和页面 API。把需要的能力对应到真实接口；没有的系统能力不能通过编造 API 获得。若受框架限制，说明具体限制和可实现方案。

## 选择页面方式和布局

- 有输入区、结果区、多个操作区、网格或复杂状态的软件，使用 `definePage` 页面及业务 CSS；不要为了省事把所有控件塞进一个纵向列表。
- 只有内容确实是简短表单或顺序动作时才用原生结构化 `column/row/card`。`row` 横向等分，`column` 纵向排列；组件树必须表达实际布局。
- 页面 CSS 必须列入 `view.styles`，文件名与 `resources` 的键准确一致。写了 CSS 但没打包/引用等于没做布局。
- 宿主已经提供左菜单、页面容器、黑白灰主题和公共控件。不要再画一套导航栏，不覆盖全局 `body`、框架组件或其他插件的样式。业务样式使用自己的根 class。
- 先确定区域层级、对齐、网格列数和剩余空间的分配，再填充控件。使用 `minmax(0,1fr)`、`min-width:0` 和合理最大宽度，避免窄屏溢出或宽屏把单个按钮拉成整页长条。
- 结果和主操作必须易于看到；长内容在明确的内容区滚动。触控目标、数字、名称、错误信息要可读，不靠占位文案或假数据充当完成。
- 默认使用现有黑白灰主题，不随意换色、字体、间距和既定排版。业务图形确有语义需要时才使用语义色。

## 行为、状态与生命周期

先写独立业务函数，再把输入、操作和显示连接起来。列出正常、空输入、非法输入、边界值、连续操作和失败后的恢复情况。每个可见按钮必须有真实行为；不要放未接通的按钮或假进度。

`setData` 是页面内存状态，不能保证切页或重启后保留。明确哪些状态临时、哪些需要持久保存；使用实际可用的插件状态接口或已确认业务存储，不将用户数据写入发布包的初始 state。不要猜一个未声明的 native 方法。密码、Cookie、Token 只由宿主代用。

页面隐藏时停止不必要的轮询，卸载时清理监听、计时器和订阅；异步结果返回前确认仍属于当前页面/请求。对有副作用的动作防止重复提交；未知结果先核对，不自动重发。不要用定时整页 reload 更新数据。

插件有安装、更新/替换、停用、卸载几种生命周期动作。替换或重写已有软件时沿用原插件 ID 更新安装，不要把新版装成新 ID 而把旧插件留在设备上；更新后旧 revision 的页面与在途调用失效，迟到结果不能写回。停用只停用、保留插件数据，卸载才清理安装态；判断、发起与核对方式见 [插件开发技能](SKILL.md) 与 [宿主契约](host-contract.md)。卸载不删除 `/PLUGINS/<id>/` 源码，只有用户明确要求清理开发源码时，才用文件工具删除明确归属的 `/PLUGINS/<id>/`，不按关键词全局搜索删除。

## 实现与验收闭环

1. 在 `/PLUGINS/<id>/` 保存可维护的源码与资源，用程序序列化生成包，不手工转义长脚本。只修改当前插件。
2. 检查入口导出、资源引用、接口与权限声明。对独立业务函数执行输入/输出测试，包括错误和边界情况。安装校验只证明包结构被接受。修改与复测优先用 [预览通道](preview-api.md) 打开已有草稿包（`packagePath="/PLUGINS/<id>/package.json"`），减少临时安装包与调试版本链；确需正式安装时才安装。
3. 安装后实际执行核心操作：输入→操作→结果→继续操作；有持久化时检查切页和重新打开；核对错误恢复、返回、滚动和启停。替换或卸载后用工具核对真实状态：安装列表、读取与调用、页面入口、后台计划与插件状态，不以菜单消失或安装成功代替清理结果。
4. 在可用设备/预览环境查看真实渲染。检查窄屏和宽屏的区域分配、换行、对齐、溢出、按钮是否可见，尤其核对样式资源是否加载。没有可用的操作/截图工具就明确“视觉或真机待验收”，不能把源码推断、生成设计图或安装成功写成实测通过。
5. 发现问题要回到布局、状态或能力契约修复；不要追加该应用专用的提示词来掩盖框架用法问题。复测失败场景，再交付。

开发过程中用简短消息报告真实阶段和发现；不要一直沉默直到最终答案，也不要逐条复述每次工具调用。最终说明可用能力、实际测试、仍未验证的部分，并给用户可打开的产物。不要宣称“所有情况都通过”而没有证据。

宿主维护本文件及 `host-contract.md`、`page-api.md`，随 App 更新。个人偏好、项目经验和补充规则写在 Bot 记忆或自己的 SKILL.md 中，避免写入会被更新的框架参考。
